# World Mini App platform capability surface (MiniKit 2.0, late 2026)

_From official docs (lane 3). This is the constraint set every app candidate was scored against._

## MiniKit commands
- **pay** — Requests a payment from the user's World Wallet inside World App (abstraction over a simple transfer); supports WLD and all local stablecoins (USDC, EURC, wARS, wCOP, wMXN, wBRL, wPEN, wCLP); returns transactionId that must be verified server-side via the Developer Portal transaction API. ([src](https://docs.world.org/mini-apps/commands/pay.md))
- **walletAuth** — Sign-In with Ethereum (SIWE v3+) authentication using the user's World App smart wallet; returns/repairs the wallet address and populates username + profile picture; nonce must be alphanumeric, 8+ chars, no hyphens. ([src](https://docs.world.org/mini-apps/commands/wallet-auth.md))
- **sendTransaction** — Submits one or more batched World Chain (chainId 480) transactions from pre-encoded calldata as an ERC-4337 user operation; returns userOpHash (not a tx hash) polled via GET developer.world.org/api/v2/minikit/userop/{hash}; Permit2 AllowanceTransfer recommended, approvals auto-revoked after the tx; every contract/token must be whitelisted in Developer Portal > Permissions. ([src](https://docs.world.org/mini-apps/commands/send-transaction.md))
- **signMessage** — Signs an EIP-191 personal message with the user's World App wallet. ([src](https://docs.world.org/mini-apps/commands/sign-message.md))
- **signTypedData** — Signs an EIP-712 typed payload; deprecated in MiniKit 2.x (wagmi web path preferred). ([src](https://docs.world.org/mini-apps/commands/sign-typed-data.md))
- **attestation** — Requests a signed app-attestation token (JWT) for a requestHash from World App, with integrity checks — lets a backend verify the action really came from a World App session. ([src](https://docs.world.org/mini-apps/commands/attestation.md))
- **sendNotification (server-side push)** — Localized push notifications sent to users' World App via POST developer.worldcoin.org/api/v2/minikit/send-notification (up to 1000 wallet addresses per send, auto language match) or manually from the Developer Portal; requires user permission via requestPermission; unverified apps limited to 40 notifications per 4 hours. ([src](https://docs.world.org/mini-apps/commands/how-to-send-notifications.md))
- **requestPermission / getPermissions** — Asks the user for and reads back mini app permissions: notifications, contacts, microphone. ([src](https://docs.world.org/mini-apps/commands/request-permission.md))
- **shareContacts** — Opens the native World App contact picker so users can share contacts with the mini app (address book/usernames resolution available). ([src](https://docs.world.org/mini-apps/commands/share-contacts.md))
- **share** — Opens the native OS share sheet from the mini app. ([src](https://docs.world.org/mini-apps/commands/share.md))
- **chat (World Chat)** — Opens World Chat with a prefilled message — the official viral-loop/invite primitive for mini apps. ([src](https://docs.world.org/mini-apps/commands/chat.md))
- **sendHapticFeedback** — Triggers native haptic feedback (game-feel primitive). ([src](https://docs.world.org/mini-apps/commands/send-haptic-feedback.md))
- **close** — Programmatically closes the mini app. ([src](https://docs.world.org/mini-apps/commands/close-miniapp.md))
- **microphone** — Mini apps can capture the device microphone inside the World App webview (microphone-stream-started/ended commands) after requesting the microphone permission. ([src](https://docs.world.org/mini-apps/reference/microphone.md))
- **MiniKit init state (user/device/location)** — On launch MiniKit exposes walletAddress, username, profilePictureUrl, verificationStatus (isOrbVerified/isDocumentVerified/isSecureDocumentVerified), preferredCurrency, pendingNotifications, device OS/safe-area insets, and normalized launch location (chat|home|app-store|deep-link|wallet-tab). ([src](https://docs.world.org/mini-apps/quick-start/init.md))
- **EIP-1193 provider + wagmi connector (MiniKit 2.0)** — MiniKit 2.0 ships getWorldAppProvider() (maps eth_requestAccounts→walletAuth, eth_sendTransaction→sendTransaction, eth_chainId→0x1e0/480) and a worldApp() wagmi connector from @worldcoin/minikit-js/wagmi, so one web app runs in browsers and inside World App (often ~2 lines of change); every command returns { executedWith: 'minikit'|'wagmi'|'fallback', data } with custom fallbacks for standalone use. ([src](https://docs.world.org/mini-apps/migration/minikit-v2))
- **leaderboards** — NOT FOUND — no leaderboard command exists in the MiniKit 2.x command set or the current docs index (docs.world.org/llms.txt) as of 2026-11; must be built app-side (sendTransaction + backend). ([src](https://docs.world.org/mini-apps/quick-start/commands.md))
- **points / v2 points API** — NOT FOUND — no points API in the current developer docs or Developer Portal API reference; the legacy world-id-docs repo was archived 2026-02-16 and its replacement contains no points endpoints. ([src](https://docs.world.org/llms.txt))
- **ticket payments** — NOT FOUND — the MiniKit v1 getTicketPaymentLink command is absent from the MiniKit 2.x command list and the current docs index; payments today go through pay / sendTransaction. ([src](https://docs.world.org/mini-apps/quick-start/commands.md))

## Stack requirements
A Mini App is any HTTPS-hosted web app rendered in a World App webview (Android WebView / iOS WKWebView). MiniKit-JS (@worldcoin/minikit-js) is framework-agnostic (React via MiniKitProvider, or vanilla JS via CDN), but the official scaffold is Next.js 15 (npx @worldcoin/create-mini-app@latest, pnpm recommended) and the docs' web-to-miniapp migration guide is Next.js + viem specific. Hard technical requirements: HTTPS/TLS (explicitly required, e.g. for Apple/Google Pay); client-side rendering — SSR must be disabled (dynamic(..., { ssr: false })) because MiniKit depends on window.WorldApp; World Chain chainId 480 mainnet (viem 'worldchain' chain) with a World Chain Sepolia testnet; a backend is expected for payment nonces, server-side payment/proof verification (Developer Portal API with Bearer key), and RP signatures. There is no JSON app manifest file — app metadata (name, square non-white-background icon, 345x240 content card PNG @3x, <25-word description, base URL) and the contract/token whitelist are configured in the Developer Portal. Webview constraints: no opening new windows, no JS alert dialogs on iOS, cookies/localStorage, geolocation, camera and file uploads OK with user permission; UI must be mobile-first with 2–3s max initial load.

## Gas / paymasters
Three layers. (1) World App built-in: World App sponsors gas for most World Chain transactions initiated by World-ID-verified users via a paymaster behind an ERC-4337 user-op flow — users never hold ETH; subject to transaction minimums/restrictions (FAQ). MiniKit sendTransaction returns a userOpHash whose final tx_hash is polled from GET /api/v2/minikit/userop/{hash}; contracts and Permit2 tokens must be pre-whitelisted in Developer Portal > Permissions (non-whitelisted = invalid_contract error; there is also a daily_tx_limit_reached error code). (2) Chain-level primitive: World Chain offers 'a free gas allowance for verified humans' funded by the World Foundation, plus Priority Blockspace for Humans (top-of-block inclusion for verified users); docs describe the mechanism (AA-level World ID-gated EIP-4337 paymaster vs sequencer-level reimbursements) with 'more details coming soon'. (3) MiniKit 2.0 / third-party (as of the 2026-03-31 launch post): built-in gas sponsorship for World Chain apps via Privy, powered by ZeroDev AA. Officially documented paymaster/bundler providers on World Chain mainnet + Sepolia: Pimlico (verifying paymaster = you sponsor gas from a Pimlico balance/card, billed monthly with ~10% surcharge on pay-as-you-go, mainnet needs a paid plan while testnets are free; sponsorship policies cap globally/per-user/per-userOp, e.g. '5 sponsored transfers per user per day'; ERC-20 paymaster = users pay gas in USDC/USDT/EURe), Alchemy paymasters, and Thirdweb ERC-4337 smart accounts.

## World ID verification patterns
Since MiniKit 2.0, World ID verification is NOT part of MiniKit — it moved to @worldcoin/idkit (IDKitRequestWidget). Inside World App, IDKit automatically uses the native World App transport (no QR); the same widget works standalone via QR/connect URL. Flow: backend signs each request (RP signature), user approves in World App / World (Authenticator) app, backend forwards the full IDKit result to POST https://developer.world.org/api/v4/verify/{rp_id} (accepts protocol 4.0 and legacy 3.0 proofs; app_id still accepted; legacy /api/v2/verify remains for old Cloud actions). Credential presets map to assurance: proofOfHuman (Orb, group_id 1 — strongest sybil resistance / one-human-one-action), selfieCheck (device-camera liveness, lower friction), passport (unique government document). Verify-once / 'has this human done X before' is exactly the nullifier pattern: each uniqueness proof carries a per-user-per-action nullifier; store used nullifiers (backend DB or on-chain mapping) and reject reuse — enforced server-side with /v4/verify or contract-side via on-chain verification: WorldIDVerifier.verify on World Chain mainnet (proxy 0x00000000009E00F9FE82CfeeBB4556686da094d7) for v4 proofs, or WorldIDRouter.verifyProof for legacy v3 proofs, both shown in docs with 'if (nullifierUsed[nullifier]) revert' sybil-resistance snippets; docs recommend deploying contracts behind an upgradable proxy for World ID 4.0 evolution. For returning-user re-verification without full uniqueness, session proofs: IDKit.createSession yields session_id (account identity across checks) plus session_nullifier (per-proof replay protection); session IDs alone don't prevent double enrollment, so create the session with a uniqueness proof first. Client-side MiniKit.user.verificationStatus (isOrbVerified/isDocumentVerified) is convenience metadata, not a verifier-grade proof. A Sandbox environment (isolated, production-like) exists for end-to-end testing incl. Selfie Check.

- Direct user payments: MiniKit pay command — instant transfers of WLD and local stablecoins (USDC, EURC, wARS, wCOP, wMXN, wBRL, wPEN, wCLP) from the user's World Wallet, with server-side confirmation via GET developer.worldcoin.org/api/v2/minikit/transaction/{transactionId}?app_id=...&type=payment — source: https://docs.world.org/mini-apps/commands/pay.md
- Arbitrary on-chain value flows (mints, NFTs, in-game assets, token swaps) via sendTransaction with Permit2 batched approve+call — source: https://docs.world.org/mini-apps/commands/send-transaction.md

## Submission / review process
1) Create the app in the Developer Portal (developer.worldcoin.org / developer.world.org) — a World App app ID is issued; configure name, icon (square, non-white background), 345x240 content card, <25-word description, and base URL; add API key; under Mini App > Permissions whitelist every Permit2 token and contract entrypoint your app touches. 2) Develop against the World ID Sandbox for verification flows and test the deployed URL by scanning the generated QR code (world.org/mini-app?app_id=...) in World App. 3) Self-check against App Guidelines (mobile-first UI, 2–3s load, no 'World'/generic terms in name, no NSFW/impersonation, privacy consent + data minimization), App Review Guidelines, Notification Guidelines, and Smart Contract Development Guidelines if contracts custody assets (immutable custody contracts or TFH-held 1-of-2 multisig upgrades with 48–72h notice, ≥90% test coverage on custody logic, repo shared with the TFH review team, OpenZeppelin + Checks-Effects-Interactions). 4) Submit for review inside the Developer Portal — approval is mandatory before public listing; the review team checks completeness (no demo/beta), a live working IDKit/MiniKit integration, and safety/legal compliance, with rationales given for rejections (re-submit after remediation; repeated same-reason failures slow subsequent reviews). 5) Once approved, the mini app is discoverable by all World App users in the Mini Apps section / app store; user reports can trigger removal at World App's sole discretion; rejection follow-up via Telegram @MateoSauton.
